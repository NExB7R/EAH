# دليل تشغيل وتطوير EAH

آخر مراجعة: 2026-11-01. هذا الملف يربط معايير المنتج وسير التغيير والتحقق وتسجيل الأخطاء في مرجع عملي واحد.

## 1. ترتيب المصادر

- الأدوار الظاهرة والصلاحيات: docs/ROLES_MATRIX.md.
- السمعة والتوثيق وخصوصية المشتري: docs/REPUTATION_POLICY.md.
- قاعدة البيانات والأمان: docs/DATABASE_RULES.md وdocs/SECURITY.md وملفات docs/migrations.
- المعيار البصري: docs/DESIGN_SYSTEM.md مع عقد الكارد وصفحة النشاط في docs/ROLES_MATRIX.md.
- سجل الأخطاء: docs/ERROR_REGISTER.md.
- حالة التقدم: أول قسم «الحالة الحالية» في docs/PROGRESS.md؛ لا تعتمد على قوائم تاريخية قديمة كدليل على نجاح اختبار اليوم.
- عند التعارض، الكود وسجلات النشر/قاعدة البيانات هي دليل الحالة الفعلية ثم تُحدّث الوثائق. لا تكتب «تم» قبل وجود دليل تحقق.

**سير العمل المعتمد:** التعديلات الجديدة تتم على `main` فقط. لا تنشئ فروع عمل أو Preview branches جديدة. ارفع التغييرات كتقدم عادي إلى آخر commit متوقع، وسجّل حالة البناء والاختبارات الفعلية؛ لا تعتبر `READY` وحدها دليلًا على اكتمال رحلة المستخدم.

## 2. نطاق المنتج

تعتمد المنصة ثلاثة أدوار فقط: الأدمن (super_admin)، البايع (merchant)، والمشتري (customer). الزائر (guest) حالة وصول غير مسجلة وليست دورًا ولا تُخزّن في user_roles. لا تستخدم مسميات بديلة ولا تنشئ دورًا رابعًا. افصل الدور عن ملكية النشاط وحالة الحساب والاشتراك والتحقق والنشر. لا تستنتج دور البايع من ملكية النشاط؛ اقرأ الدور من user_roles وافحص الملكية بصورة مستقلة. واجهة المستخدم وكل ما يظهر له بالعربية فقط وباتجاه RTL. حافظ على أسماء المسارات والقيم التقنية الحالية ما لم توجد خطة ترحيل آمنة ومختبرة.

مسار إنشاء الإدارة:
- إنشاء النشاط مستقل عن ربط البايع؛ ربط المالك اختياري.
- النشاط غير المملوك يمكن أن يظهر للعامة إذا كانت حالة النشر تسمح بذلك، لكنه لا يستقبل طلبات داخل المنصة حتى تُستوفى شروط المالك والموافقة.
- رقم التواصل الأساسي مطلوب في نموذج الإدارة؛ استكمل الوصف والعنوان والصور والمواعيد من صفحة التعديل حسب طبيعة النشاط.
- بعد الحفظ، افتح رابط النشاط العام من نتيجة الإنشاء وتأكد من الاسم والصورة والمنطقة والحالة ومعلومات التفاصيل.

مسار البايع:
- البايع يقدّم طلبًا مرتبطًا بحسابه.
- النشاط الذي ينشئه الطلب يبدأ غير منشور، وتحتاج الإدارة لمراجعته قبل عرضه.
- بعد الموافقة، يتحقق البايع من الصفحة العامة؛ نجاح حفظ النموذج وحده لا يثبت الظهور العام.

## 2.1 سياسة السمعة والتوثيق

اتبع `docs/REPUTATION_POLICY.md`: توثيق النشاط وتقييمه وسجل الطلبات المكتملة حقائق منفصلة، ونقاط `trust_score` هي نقاط مشاركة داخلية فقط. لا تعرض درجة موثوقية للمشتري بشكل عام ولا تخفض السمعة بسبب بلاغ معلّق أو إلغاء غير محدد المسؤولية.

## 3. عقد الكارد

المطلوب أن يفهم المشتري خلال ثوانٍ: ما اسم النشاط؟ نوعه ومكانه؟ هل هو مفتوح؟ هل له تقييم؟ هل توجد عروض أو فروع أو قناة طلب مفعّلة؟ ثم يكون هناك إجراء رئيسي واحد واضح لعرض التفاصيل.

- مساحة الصورة ذات نسبة ثابتة مع بديل للشعار/الصورة الناقصة.
- اسم النشاط يظهر بوضوح وبحد سطرين، والموقع والنوع لا يختلطان بالشارات.
- التقييم وعدد مراجعاته يظهران معًا؛ عند عدم وجود تقييمات نعرض ذلك بصدق.
- شارات المميز والجديد والموثق تعتمد على بياناتها الحقيقية فقط.
- الوصف يأتي من hook ثم description كبديل، مع قص نظيف.
- حالة الفتح تراعي توقيت مصر والمواعيد والتجاوز اليدوي.
- لا نعرض زر «اطلب الآن» إذا كان الضغط يفتح صفحة التفاصيل فقط.

## 4. عقد صفحة النشاط

ترتيب الصفحة: غلاف وهوية النشاط والشعار والاسم؛ النوع والمكان وحالة الفتح والتوثيق والتقييمات ومؤشرات الثقة المعروفة؛ إجراءات التواصل/الطلب المصرح بها؛ تبويبات المعلومات والعروض والمنيو/الصور والتقييمات والتعليقات؛ ثم الأنشطة المشابهة.

- بيانات الاتصال الخاصة لا تظهر في الاستجابة العامة؛ استخدم مسار التواصل المراجع أمنيًا.
- حافظ على RTL والموبايل، وحالات التحميل والخطأ، وعناوين قابلة للقراءة وإتاحة لوحة المفاتيح.
- لا نعرض رقمًا أو شارة أو زرًا اعتمادًا على تخمين؛ عند نقص البيانات، أظهر حالة فارغة أو أخفِ الوحدة حسب التصميم.

## 5. خريطة الملفات

- كارد النشاط: web/components/business-card.tsx وweb/components/business-card.module.css.
- رأس صفحة النشاط: web/components/business-hero.tsx وweb/components/business-hero.module.css.
- تركيب الصفحة العامة: web/app/businesses/[slug]/page.tsx وbusiness.module.css.
- إنشاء الإدارة: web/app/admin/businesses/new وما يتصل به في web/app/admin/businesses/actions.ts.

ابحث عن مكوّن موجود قابل لإعادة الاستخدام قبل إنشاء واحد جديد. لا تنشئ مكوّنًا ثانيًا للكارد أو لشارة الحالة من غير سبب موثق. لا تقسّم ملفًا أو تعيد ترتيبه لمجرد الشكل إذا لم يقلل التعقيد أو يمنع أخطاء.

## 6. بوابة الجودة لكل تغيير

1. اقرأ الأجزاء المتعلقة بالمسار والأمان والأدوار قبل التعديل.
2. اعمل تعديلًا صغيرًا متماسكًا على `main` مع commit يشرح السبب.
3. لتغييرات TS/TSX وCSS، تحقق من TypeScript وESLint وPrettier وStylelint وVitest ثم npm run build حسب الملفات المتأثرة.
4. راجع Vercel Preview؛ تحقق من READY ثم افتح المسار المتأثر فعليًا. نجاح Build لا يثبت صحة كل التدفقات.
5. إذا فشلت GitHub Actions دون تشغيل خطوات (runner_id يساوي 0 ولا توجد steps/logs)، سجّلها كعائق تشغيل CI، لا كخطأ كود أو نجاح اختبارات.
6. لا تدمج إلى main ولا تطبق migration إنتاجية اعتمادًا على بناء فقط. ترحيلات قاعدة البيانات تحتاج مقارنة schema وخطة rollback/backup واختبارات RLS وE2E وقرار إطلاق منفصل.
7. لا تنشر أسرارًا أو مخرجات بيئة ولا تطلب من المستخدم لصق مفاتيح سرية.

## 7. سجل الأخطاء

لكل مشكلة، سجّل معرّفًا والحالة والأثر وخطوات إعادة الإنتاج والملف والسبب المثبت والإصلاح وما يثبت نجاحه. افصل بين «تم التعديل» و«تم التحقق». إذا ظهرت مشكلة جديدة أثناء الاختبار، أضفها قبل الانتقال لتحسين تجميلي جديد.

- OPEN: لم يبدأ الإصلاح.
- IN PROGRESS: الإصلاح جارٍ.
- FIXED — VERIFY: المصدر اتعدل لكن التحقق لم يكتمل.
- VERIFIED: نجح اختبار محدد أو فُتحت صفحة معاينة محددة؛ دوّن الدليل.
- BLOCKED — INFRA: الاختبار متعذر بسبب البيئة/الصلاحيات، مع حفظ رابط السجل.

## 8. سجل جلسة العمل

في نهاية كل دفعة، حدّث docs/ERROR_REGISTER.md وdocs/PROGRESS.md بما تغيّر فعلًا، والفرع والـ commit ونتيجة Build والمسارات المختبرة وما بقي مفتوحًا. الهدف أن يستطيع المطور التالي الاستكمال من هذه الملفات وسجلات GitHub/Vercel بدل إعادة الفحص من الصفر.
