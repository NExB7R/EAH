# EAH — مصفوفة الأدوار والصلاحيات

> المرجع الأساسي للأدوار الظاهرة في المنتج، ومَن يقدر يعمل إيه. آخر مراجعة: 2026-11-01.

## الأدوار المعتمدة

تحتوي المنصة على ثلاثة أدوار فقط: الأدمن والبايع والمشتري. الزائر حالة وصول غير مسجلة، وليس دورًا رابعًا. لا يجوز إنشاء دور إضافي أو استخدام مسمى بديل:

| المسمى الظاهر | المفتاح الداخلي | الوظيفة |
|---|---|---|
| الأدمن | `super_admin` | إدارة المنصة والمستخدمين والأنشطة والإعدادات والصلاحيات الإدارية |
| البايع | `merchant` | إدارة نشاط واحد مرتبط بحسابه حاليًا، وفق صلاحيات الخادم وقاعدة البيانات |
| المشتري | `customer` | استخدام خدمات المشتري والتصفح والطلب والتفاعل المسموح |


**مهم بشأن التخزين:** تُحفظ أدوار الحسابات المسجلة في `user_roles` بالقيم الداخلية الحالية `super_admin` و`merchant` و`customer`. الزائر حالة وصول غير مسجلة داخل التطبيق فقط، ولا تُنشأ له سجلات في `user_roles`.

**فصل الدور عن الحالة والعلاقة:** الدور يحدد نوع الصلاحيات العامة، بينما ملكية النشاط وعلاقة الحساب به، وحالة الحساب، والحظر، والتحقق، والاشتراك، والنشر، وحالة النشاط، وتفعيل استقبال الطلبات بيانات مستقلة. لا تستنتج دور التاجر من مجرد وجود نشاط مرتبط بالحساب؛ اقرأ الدور من سجل الدور المعتمد، وافحص الملكية منفصلة. لا تحول أي حالة من الحالات السابقة إلى دور.

لا تُعد القيمة التاريخية `admin` دورًا خامسًا أو صلاحية إدارية؛ لا تمنحها صلاحيات، ولا تعرضها للمستخدم كدور مستقل. صلاحية الإدارة الكاملة محصورة في `super_admin`.

## قيد مساحة التاجر الحالية

- يعمل مسار تقديم طلب النشاط ولوحة التاجر الحالية على نشاط واحد مرتبط بكل حساب تاجر.
- لذلك لا تعرض قائمة ربط النشاط حسابًا مرتبطًا بالفعل بنشاط آخر، ويرفض الخادم أي ربط ثانٍ حتى يُفك الارتباط الأول.
- يستطيع الأدمن إنشاء أي عدد من الأنشطة دون ربط حساب تاجر؛ لا يؤثر عدم وجود تاجر مرتبط في ظهور النشاط العام إذا كان منشورًا.
- هذا القيد يصف سلوك لوحة التاجر الحالية، وليس قيدًا على عدد الأنشطة التي يستطيع الأدمن إنشاؤها. توسيع التاجر لإدارة عدة أنشطة يتطلب لوحة اختيار نشاط وسياقًا واضحًا لكل إجراءات التاجر قبل تغيير القيد.

## مصدر الصلاحيات

- صلاحية الإدارة الكاملة تُمنح فقط للحساب ذي الدور `super_admin`، وتُفرض في حارس الخادم وRLS ومشغّل قاعدة البيانات.
- علاقة التاجر بالنشاط تُحسم من owner_profile_id وسياسات الوصول، وليس من اختيار المستخدم كلمة «تاجر» في نموذج.
- العميل يستطيع تصفح الصفحات العامة، وإنشاء حساب، واستخدام ميزات العميل المسموحة.
- كل Server Action أو API محمي لازم يتحقق من الجلسة والملكية/صلاحية الإدارة على الخادم قبل الكتابة.
- تظل القيم الداخلية والمسارات الحالية كما هي حتى لا تتعطل redirects أو سياسات RLS؛ المطلوب توحيد التسميات الظاهرة أولًا.

## دورة إضافة النشاط

### الأدمن — إنشاء مباشر
1. تفتح الإدارة نموذج نشاط جديد.
2. لا يُطلب رقم هاتف شخصي للمالك كي ينشئ الأدمن النشاط. بيانات التواصل العامة للنشاط منفصلة عن رقم المالك، وتُدار وفق حقول النشاط المتاحة.
3. ربط تاجر بالنشاط اختياري.
4. عند اختيار حساب، يُربط النشاط بذلك الحساب بوصفه المالك، وتصبح له صلاحيات إدارة النشاط وفق حراس الخادم وRLS.
5. عند عدم اختيار تاجر، يظل النشاط منشورًا للعامة إذا كانت حالة النشر تسمح بذلك؛ لا يتحول تلقائيًا إلى حساب مالك.
6. لا تُفعّل طلبات المنصة للنشاط غير المملوك أو غير المعتمد لاستقبال الطلبات.

### التاجر — تقديم طلب
1. يقدّم التاجر الطلب من حسابه.
2. يلزم إدخال بيانات النشاط والتواصل والموقع المطلوب في النموذج.
3. ينشأ الطلب غير منشور؛ لا يُعلن ظهوره للزوار قبل اعتماد الإدارة.
4. بعد الموافقة، يراجع التاجر صفحته العامة وبياناتها وصورها ومواعيد العمل.

## عقد كارد النشاط

الكارد يوضح للعميل خلال ثوانٍ: اسم النشاط، النوع، المكان، هل هو مفتوح، هل له تقييم، وهل توجد عروض أو فروع أو قناة طلب مفعّلة. ثم يوفّر إجراء رئيسيًا واحدًا يناسب وجهته.

- صورة الغلاف أو بديل الشعار تظهر بنسبة ثابتة مع تباين مناسب.
- الاسم يظهر بوضوح، والموقع والنوع لا يختلطان بالشارات.
- التقييم وعدد التقييمات يظهران معًا؛ عند عدم وجود تقييمات نعرض ذلك بصدق.
- شارات المميز والجديد والموثق تعتمد على بياناتها الحقيقية فقط.
- الوصف المختصر يأتي من hook ثم description كبديل، مع قص نظيف.
- حالة الفتح تعتمد على التوقيت المصري والمواعيد والتجاوز اليدوي عند وجوده.
- لا تعرض زر «اطلب الآن» إذا كان الضغط يفتح صفحة التفاصيل فقط.
- لا تضع أرقام الهاتف/واتساب الخاصة داخل payload عام؛ استخدم مسار التواصل المصرح به فقط.

## عقد صفحة النشاط

يجب أن توضح الصفحة: الغلاف والشعار والاسم، النوع والمكان وحالة الفتح، التوثيق والتقييمات، وصف النشاط، وسائل التواصل المتاحة بأمان، ساعات العمل والعنوان والخريطة، الصور/المنيو والعروض إن وجدت، التقييمات والتعليقات، والأنشطة المشابهة عند توافرها. أخفِ الوحدات غير المتاحة أو اعرض حالة فارغة واضحة بدل بيانات وهمية أو مساحات بلا معنى.

لا تعرض إجراءً لا يحق للمستخدم تنفيذه. الطلبات الداخلية لا تظهر كمتاحة إلا عندما تسمح أعلام الإدارة والتاجر والنشاط وساعات العمل بذلك.

## سياسة السمعة والتوثيق

تطبق `docs/REPUTATION_POLICY.md` مع مراعاة الأدوار الثلاثة وحالة الزائر:
- **التاجر:** تظهر للعميل شارة التوثيق الإداري، متوسط التقييم وعدده، وعدد الطلبات المكتملة كحقائق منفصلة. لا تظهر نقاط المشاركة أو مستوياتها على كارد النشاط أو صفحته.
- **العميل:** لا يملك درجة سمعة عامة يمكن البحث عنها برقم الهاتف. يرى التاجر فقط توثيق الهاتف وعدد الطلبات المكتملة في سياق طلب تابع لنشاطه، مع توضيح محايد عند غياب البيانات.
- **الأدمن:** يرى نقاط المشاركة لأغراض النظام الداخلي، بينما قرارات التوثيق والبلاغات والعقوبات تسجل بأدلة وسبب واضح.
- **الزائر:** يرى المعلومات العامة المنشورة فقط، ولا يملك تفاعلات أو صلاحيات حساب مسجل.
- لا تؤثر الإعجابات والتعليقات والمشاهدات وتسجيل الدخول والإحالات في ترتيب السمعة. ولا ينقص بلاغ معلّق أو إلغاء غير محدد المسؤولية من موثوقية العميل.
- القيم الداخلية `trust_score/trust_tier` محفوظة للتوافق التاريخي، لكنها لا تعني سمعة ولا تستخدم لترتيب أنشطة الجمهور.

## مصفوفة الوصول

| المسار | زائر | عميل | تاجر | الإدارة |
|---|:---:|:---:|:---:|:---:|
| الصفحات العامة والاكتشاف وتفاصيل الأنشطة المنشورة | نعم | نعم | نعم | نعم |
| حساب العميل | تسجيل دخول | نعم | نعم | إعادة توجيه لمسار الإدارة حسب القواعد الحالية |
| تقديم طلب إضافة نشاط | حسب بوابة التسجيل الحالية | نعم | ممنوع إذا كان لديه نشاط بالفعل وفق القاعدة الحالية | ممنوع |
| لوحة التاجر وتعديل نشاطه | ممنوع | ممنوع | النشاط المملوك فقط | لا تستخدم بدل لوحة الإدارة |
| لوحة الأدمن وإضافة/مراجعة/أرشفة أي نشاط | ممنوع | ممنوع | ممنوع | نعم |

هذه المصفوفة تصف السلوك المستهدف في الواجهة، وتظل حراس الخادم وسياسات قاعدة البيانات المرجع النهائي. إذا اختلف التنفيذ معها، سجّل الاختلاف وأصلحه مع اختبارات بدل تعديل التوثيق لإخفائه.

## قواعد التغيير

1. تغيير نص المستخدم لا يغيّر قيمة role الداخلية أو مسارًا أو سياسة RLS.
2. أي تغيير في الملكية/النشر يحتاج تحققًا بخادم التطبيق وقاعدة البيانات.
3. أي تعديل UI يراعي RTL والموبايل وحالات البيانات الناقصة والتحميل والخطأ.
4. لكل إصلاح حالة موثقة: مفتوح، قيد الإصلاح، تم إصلاحه ويحتاج تحقق، أو تم التحقق منه.
