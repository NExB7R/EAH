# EAH — استراتيجية اختبار QA

> **الحالة الحالية — 2026-11-20:** لا توجد قاعدة Supabase مستقلة غير إنتاجية تم التحقق من اتصالها واعتمادها. هذا الملف لا يثبت وجود بيئة QA نشطة، ولا يجيز استخدام أي بيانات اختبار تاريخية.

## قواعد ملزمة

- الإنتاج للقراءة العامة فقط أثناء هذه المرحلة؛ لا تنشئ أو تعدّل أو تحذف حسابات أو أنشطة أو طلبات أو تقييمات أو صورًا أو إعدادات في Supabase الإنتاجي.
- أي سجل تاريخي يحمل اسمًا أو slug تجريبيًا لا يُعد دليلًا على أنه موجود في قاعدة معزولة. لا تستخدم هذه السجلات للاختبار ولا تنظفها دون جرد موثق وموافقة منفصلة.
- لا تشغّل docs/seeds/cleanup.sql ولا أي seeder في الجلسة الحالية.
- لا تحفظ كلمات مرور أو مفاتيح أو UUIDs لحسابات أشخاص في Git. أي كلمة مرور ثابتة سبق نشرها في المستودع تُعامل على أنها مكشوفة وتحتاج تدويرًا بعد تحديد الحسابات الفعلية من مالك المشروع.
- الأدوار الظاهرة حصريًا: الأدمن (super_admin)، العميل (customer)، والتاجر (merchant). لا تغيّر مفاتيح الأدوار التقنية.

## seeder الحالي

الملف web/scripts/seed-qa-accounts.mjs يستخدم Service Role ويكتب في Supabase Auth والجداول المرتبطة بالحسابات والأنشطة وإعدادات الطلب. يحتوي على شروط تفعيل صريحة، ويفحص Project Ref الإنتاج المعروف، ويتطلب تطابق EAH_QA_ALLOWED_PROJECT_REF مع المشروع المستهدف.

هذه الحواجز لا تجعل التشغيل آمنًا تلقائيًا. قبل أي تشغيل مستقبلي يجب:
1. اعتماد مشروع Supabase مستقل عن الإنتاج والتحقق من Project Ref وURL من لوحة Supabase.
2. تخصيص مفاتيح وSecrets منفصلة تمامًا عن الإنتاج.
3. مراجعة السكريبت وحارس منع الإنتاج على النسخة التي سيتم تشغيلها.
4. التأكد من أن المشروع المستهدف هو نفسه المسموح به، ثم تشغيل seeder على QA فقط.
5. الاحتفاظ ببيانات الدخول الناتجة محليًا في ملف مستثنى من Git وبصلاحيات وصول مقيدة.

لا توجد حاليًا قيمة Project Ref غير إنتاجية معتمدة لهذا الغرض؛ لذلك لا تضبط متغيرات التفعيل أو السماح ولا تشغّل السكريبت.

## خطة التحقق عند توفر QA

### الزائر
- [ ] الصفحة الرئيسية والاستكشاف وصفحة النشاط المنشور تعمل.
- [ ] المسودات والأنشطة غير المنشورة لا تظهر في البحث أو الصفحات العامة.
- [ ] لا تتسرب أرقام الهاتف أو واتساب الخاصة إلى HTML أو RSC payload أو API عامة.

### العميل
- [ ] تسجيل الدخول والجلسة والصلاحيات.
- [ ] المفضلة والمتابعة والتقييم والتعليق وكشف بيانات التواصل.
- [ ] منع التفاعلات للحساب المقيد مع الحفاظ على الإجراءات المسموحة.

### التاجر
- [ ] لا يرى أو يعدّل إلا النشاط المرتبط بحسابه.
- [ ] إحصائيات اليوم محسوبة بتوقيت Africa/Cairo.
- [ ] الطلبات الداخلية منفصلة عن واتساب، مع اختبار قبول/رفض وفشل الاتصال ومنع التكرار.
- [ ] حالات الشبكة غير المتصلة والطابور وإعادة المحاولة تعمل دون تكرار.

### الأدمن
- [ ] إنشاء نشاط بلا مالك.
- [ ] إنشاء نشاط وربط مستخدم موجود اختياريًا دون طلب هاتفه الشخصي.
- [ ] الصور والشعار والغلاف وتنظيف الملفات بعد فشل الحفظ.
- [ ] المسودة لا تظهر للعامة قبل النشر الصريح.
- [ ] بعد النشر: البحث ورابط الصفحة العامة والشعار والتفاصيل.
- [ ] العميل والتاجر لا يستطيعان الوصول إلى مسارات الإدارة.

## إثبات الاختبار

كل نتيجة يجب أن تسجل:
- SHA الدقيق للنسخة المختبرة.
- اسم بيئة QA وProject Ref غير الحساس بعد التحقق منه.
- الأمر أو سيناريو E2E ونتيجته الفعلية.
- أي فشل مع logs منقحة من الأسرار والبيانات الشخصية.

لا يُعد TypeScript أو Build وحدهما إثباتًا على سلامة صلاحيات قاعدة البيانات أو دورة إنشاء النشاط. حتى تاريخ هذا التحديث لا توجد نتائج E2E حديثة مثبتة لهذه السيناريوهات.

## بيانات QA التاريخية

كانت هناك تعليمات قديمة توثق fixtures اختبارية وتدفقات تشغيل مؤقتة على قاعدة الإنتاج. حالتها الحالية غير متحققة، وانتهت مواعيد مراجعتها التاريخية. تفاصيلها لا تُستخدم كقائمة حذف ولا كبيئة اختبار نشطة. تظل أي مراجعة مستقبلية للبيانات التاريخية منفصلة عن التطوير والاختبار، وقراءة فقط إلى أن يقرر المالك إجراءً محددًا.
