# EAH — دليل تشغيل التطوير ودورة النشاط

**آخر مراجعة:** 2026-10-27  
**حالة الإطلاق:** غير جاهز للإنتاج حتى تُغلق بوابات التحقق المحددة هنا وفي `PRODUCTION_CHECKLIST.md`.

## 1. أدوار المنصة ومصطلحات الواجهة

المنصة تعرض ثلاثة أدوار فقط:
- **الأدمن:** إدارة المنصة بالكامل، إضافة الأنشطة ومراجعة طلبات البايعين والنشر.
- **البايع:** إدارة النشاط المرتبط بحسابه، ورفع بياناته وصوره ومتابعة الطلبات المسموح بها.
- **المشتري:** اكتشاف الأنشطة والتفاعل معها والشراء/إرسال الطلب عندما يكون النشاط مؤهلًا.

قيم قاعدة البيانات الحالية مثل `admin` و`merchant` و`customer` أسماء داخلية. لا تغيّر enums أو قيم `user_roles.role` لمجرد تغيير النص الظاهر. يجب تحويل الأسماء في الواجهة ورسائل الأخطاء والإشعارات إلى المصطلحات الثلاثة أعلاه. لا تعرض `super_admin` كدور رابع؛ تعامل معه كصلاحية إدارية داخلية.

## 2. قواعد لا يجوز كسرها في دورة النشاط

1. **المالك اختياري في إنشاء الأدمن.** يجب أن يعمل الإنشاء مع `owner_profile_id = null`. وجود المالك ليس شرطًا للنشر العام.
2. **النشر مستقل عن المالك.** `is_published = true` هو شرط ظهور النشاط للزوار، ويجب أن يظهر في الاستكشاف والبحث وصفحة `/businesses/[slug]` سواء كان له بايع مرتبط أو لا.
3. **رقم النشاط ليس رقم المالك.** النموذج الإداري يطلب حاليًا رقم اتصال أساسيًا واحدًا للنشاط. لا تضع رقم مالك شخصي في حقول النشاط تلقائيًا، ولا تجعل اختياره شرطًا للنشر.
4. **ربط مالك يحدد الصلاحيات فقط.** عند اختيار حساب مشتري كمالك، تتم ترقية دوره إلى بايع عبر المسار الإداري المحمي؛ وعند تعذر الترقية يجب إلغاء الإنشاء أو التراجع عن الربط وتسجيل الفشل. لا تربط النشاط بحساب أدمن.
5. **البايع لا ينشر طلبه بنفسه.** طلب `/merchant/apply` يتطلب جلسة، ويظل تحت مراجعة الأدمن حتى الموافقة. النشر الإداري لا يجب أن يرث قيد المراجعة الخاص بطلب البايع.
6. **البيانات الخاصة تظل خاصة.** رقم الهاتف/واتساب الخاص لا يدخل في payload العام أو HTML الثابت؛ كشف الاتصال يمر عبر مسار الخادم الموثق والمحدود المعدل، مع تسجيل التدقيق. لا تُرجع صلاحيات SELECT عامة لتسهيل العرض.
7. **الحالة المفتوحة موحدة.** استخدم `isBusinessOpen` ومصدر ساعات العمل المشترك في الكارد وصفحة التفاصيل والبحث. احترم `open_now_override`، وجدول `working_hours`، وقيمة `is_open` عند عدم وجود جدول.
8. **الفشل الجزئي ممنوع قدر الإمكان.** إذا فشل حفظ الاتصالات بعد إنشاء النشاط، تراجع عن الإنشاء عند الإمكان؛ إذا فشل rollback، سجّل تفاصيل كافية في audit log وقدّم رسالة إجرائية واضحة بدل نجاح كاذب.

## 3. معيار محتوى كارد النشاط

الكارد هو ملخص للاختيار، وليس صفحة تفاصيل مصغرة. ترتيب المعلومات:
1. صورة الغلاف، ثم الشعار/الحرف البديل إذا لم تتوفر الصورة.
2. شارات موثوقة فقط: مميز، جديد، موثّق أو ترتيب فعلي في قائمة الترند.
3. اسم النشاط واضح، ثم النوع والمنطقة/المدينة.
4. حالة الفتح الحالية من المصدر المشترك.
5. التقييم وعدد المراجعات فقط إذا كان هناك تقييم فعلي؛ لا تعرض صفرًا كتقييم.
6. قناة الطلب الفعّالة فقط: طلبات داخل EAH أو واتساب، بحسب الإعداد الحقيقي.
7. عدد الفروع والعروض عندما تكون القيم أكبر من صفر.
8. رابط واضح واحد إلى التفاصيل، وتخطيط متجاوب لا يضغط النصوص على شاشة صغيرة.

لا تعرض رقم الهاتف الخاص في الكارد العام ولا تضف شارات لا تتوافق مع حالة قاعدة البيانات.

## 4. معيار صفحة النشاط

يجب أن تقدم الصفحة خلال أول شاشة: الغلاف، الشعار/بديله، الاسم، النوع، المنطقة، حالة الفتح، التقييم إن وجد، وإجراء أساسي واضح ومتاح فقط عندما يكون مؤهلًا. تحت ذلك تظهر معلومات العنوان والخريطة، مواعيد العمل، الفروع، صور النشاط/المنيو، العروض، التقييمات والتعليقات المتاحة. لا تعرض أقسامًا فارغة بشكل يضلل المشتري؛ استخدم empty state قصيرة ومقصودة. يظهر رابط إدارة النشاط للبايع المالك فقط.

كل مصدر بيانات عام يجب أن يستخدم حقولًا مسموحًا بها. لا تضف الهاتف أو معرف المالك إلى الاستعلام العام لمجرد تسهيل تنسيق الواجهة.

## 5. ترتيب دورة الإنشاء

### الأدمن
1. فتح `/admin/businesses/new` بعد التحقق من صلاحية الأدمن.
2. إدخال النوع والاسم والوصف المختصر والموقع ومعلومات اتصال النشاط.
3. اختيار بايع اختياريًا من حسابات المنصة؛ يظل المالك فارغًا عند عدم الاختيار.
4. مراجعة البيانات، ثم إنشاء سجل النشاط وجهات الاتصال.
5. عند النجاح، الانتقال إلى صفحة تعديل السجل نفسه لإضافة الغلاف والشعار والمعرض ومواعيد العمل ومراجعة حالة النشر.
6. التحقق من `is_published` وslug، ثم التحقق من الكارد ونتيجة البحث وصفحة النشاط العامة.
7. عند الربط بحساب مشتري، التأكد من تحوله إلى بايع وظهور النشاط في لوحة البايع؛ وعند عدم الربط يجب أن يظل النشاط ظاهرًا للعامة.

### البايع
1. تسجيل الدخول ثم تقديم طلب عبر `/merchant/apply`.
2. التحقق من الحقول والاتصالات والصور قبل الإرسال.
3. ظهور حالة الطلب الفعلية بوضوح: تحت المراجعة أو منشور أو مرفوض مع سبب قابل للتصرف.
4. لا تعرض رابطًا عامًا على أنه منشور قبل موافقة الأدمن.
5. بعد الربط والنشر، اختبر أن البايع المالك وحده يستطيع التعديل.

### المشتري والزائر
1. استكشاف الأنشطة والبحث عنها.
2. فتح الكارد والوصول إلى slug الصحيح.
3. التأكد من اتساق حالة الفتح وقنوات الطلب ومعلومات الصفحة.
4. لا تسمح بإنشاء طلب إذا لم يكن النشاط مؤهلًا، حتى لو كان ظاهرًا للعامة.

## 6. بوابات الفحص قبل دمج التغييرات

من مجلد `web`:
```bash

npx stylelint "app/**/*.module.css" "components/**/*.module.css"
npx vitest run --reporter=dot
npm run build
npm audit --omit=dev --audit-level=high
npx knip --include files,dependencies
```

لـ E2E، استخدم preview URL حقيقيًا وليس الإنتاج:
```bash
PLAYWRIGHT_SKIP_SERVER=1 PLAYWRIGHT_BASE_URL=https://<preview>.vercel.app npx playwright test
```

اختبارات RLS تحتاج اتصال قاعدة اختبار غير إنتاجية عبر `SUPABASE_DB_URL`. لا تطبع الأسرار في logs ولا تستخدم production connection لاختبار عشوائي.

## 7. معالجة الأخطاء وعدم تكرارها

- كل عطل متكرر ينتج عنه: سبب موثق، اختبار منع تكرار، وتحديث للـ checklist إن كان يمس دورة إطلاق.
- لا تعتبر خطأ runner نجاحًا أو فشلًا في TypeScript. إذا كان `runner_id: 0` والـ steps تساوي صفرًا، اتبع [issue #22](https://github.com/NExB7R/EAH/issues/22) وفحص إعدادات/حدود GitHub Actions.
- لا تعتبر نجاح Vercel وحده دليلًا على أن اختبار المستخدم المكتمل نجح؛ هو دليل بناء ونشر للمعاينة فقط.
- تجنب `console.log` الذي قد يكشف بيانات أو أسرارًا؛ استخدم audit/error logging في الخادم مع معرّفات سجل غير حساسة ورسائل واجهة قابلة للتصرف.
- لا تنشئ صفحة أخطاء للمستخدم. عالج الأخطاء داخل الخطوة برسالة قصيرة، وسجّل التفاصيل الداخلية، وتأكد أن عمليات الكتابة الجزئية لا تترك بيانات يتيمة.
- لا تنفّذ أي migration إنتاجية قبل مطابقة تاريخ المايجريشن بين المستودع وSupabase، ووجود backup يمكن التحقق منه وخطة rollback مراجعة.
